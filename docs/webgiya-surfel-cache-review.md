# Webgiya Surfel 캐시 검토와 PRTGI 적용안

2026-11-03에 [jure/webgiya](https://github.com/jure/webgiya)의 커밋 [`0cd7f968`](https://github.com/jure/webgiya/tree/0cd7f96859adc34e181f34a5d804e53fa94799cb)을 검토했다. README, 저자의 [구현 설명](https://juretriglav.si/surfel-based-global-illumination-on-the-web/), 아래 소스 파일을 대조했다. Webgiya 데모를 이 PC에서 실행하거나 성능을 측정하지는 않았다. 이후 첫 단계인 에셋/인스턴스 소유 GPU 표면 풀·공간 인덱스를 PRTGI에 추가하고 검증했다. 조명 캐시·반복 갱신·MSME·방향별 깊이는 아직 구현하지 않았다. [현재 구현과 검증](runtime-gi-pc.md#gpu-surfel-풀과-공간-조회--2026-11-03)을 참고한다.

## 무엇을 캐시하는가

Webgiya는 GBuffer에서 부족한 표면 표본을 찾아 GPU 풀에 Surfel을 생성한다. Surfel별로 위치·법선·생성 시점·수명, 누적 간접광, 시간 필터 상태, 방향별 표본 가중치, 주변 깊이 모멘트를 유지한다. 셀별 Surfel 목록을 구성한 뒤, 화면 픽셀과 광선 교차점 모두 같은 공간 인덱스로 주변 조명을 조회한다. 에셋마다 저장한 사전 계산 파일을 로드하는 방식은 아니다.

| 구성 | 확인한 구현 | 이 프로젝트에서의 용도 |
|---|---|---|
| GPU 풀 | [surfelPool.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/surfelPool.ts): Surfel과 시간 필터 상태 분리, 조명 상태 이중 버퍼 | 에셋 표면 데이터와 런타임 조명 상태를 분리. CPU로 SH 전체를 읽는 현재 기준 경로와 별도로 GPU 캐시 유지 |
| 수명 관리 | [surfelAgePass.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/surfelAgePass.ts): 조회 기여·밀집도에 따라 유지하거나 풀로 반환 | 화면에서 안 보이는 표면도 간접광에 기여하면 유지하되, 최대 용량과 갱신 예산을 제한 |
| 공간 인덱스 | [surfelHashGrid.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/surfelHashGrid.ts): 카메라 중심 다단계 격자, count → prefix sum → slot 목록 생성, 단계 경계 중복 삽입 | 픽셀마다 전체 Surfel을 검색하지 않고 근처 셀의 후보만 조회 |
| 광전달 | [surfelIntegratePass.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/surfelIntegratePass.ts): 삼각형 BVH 교차, 교차점 직접광과 이전 조명 캐시 합산, MSME 시간 필터 | 매 변경마다 모든 프로브의 최대 6바운스를 완성하는 대신 여러 프레임에 걸쳐 조명을 전파하는 비교 경로 |
| 방향별 가시성 | [surfelRadialDepth.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/surfelRadialDepth.ts): Surfel당 4×4 방향 표본에 깊이의 1~4차 모멘트, 퇴화 시 2모멘트 방식으로 복귀 | 화면의 반복 BVH 가시성 검사를 캐시 조회로 대체하는 후보. 얇은 벽·모서리에서 현재 정확한 BVH 경로와 비교 필요 |
| 화면 합성 | [surfelGIResolvePass.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/surfelGIResolvePass.ts): 거리·법선·생성 후 경과·신뢰도·가시성 가중치를 정규화해 주변 조명 합산 | 현재 SH 프로브 보간과 별도의 표면 캐시 합성 경로를 만들어 원형 경계·빛샘·시간 안정성을 비교 |

여기서 cascaded grid는 **Surfel 검색용 공간 해상도 단계**다. Love and Deepspace 자료의 방향 해상도·구간 병합을 포함하는 Radiance Cascade와 같은 기능으로 취급하지 않는다. 또한 Surfel을 조명 캐시로 사용하지만 광선의 실제 기하 교차는 삼각형 BVH가 담당한다. 따라서 현재 PRTGI의 BVH 기준 구현은 이후에도 교차·가시성 검증에 재사용할 수 있다.

## 그대로 연결하면 안 되는 부분

**가구 이동과 Surfel 소유권.** [sceneBvh.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/sceneBvh.ts)는 메시를 복제해 월드 변환을 적용한 뒤 하나의 BVH로 합친다. 확인한 [main.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/main.ts)의 BVH 생성 호출은 장면 로드 경로에 있으며, 프레임 루프에는 이동 메시의 BVH 갱신이 없다. Surfel 풀에도 인스턴스 ID와 로컬 표면 좌표가 없다. 따라서 이 코드를 가져오는 것만으로 방 꾸미기의 이동·회전·삭제가 해결되지는 않는다. 우리 구현에는 안정적인 인스턴스 ID, 로컬 Surfel 위치·법선, 변환 세대, 이동 전후 영향 범위가 필요하다.

**조명 단위.** 이름은 `irradiance`지만 Webgiya 적분기는 `Li × cosθ / (π × PDF)`를 누적하고 최종 합성에서 반사율을 곱한다. 식을 따라 해석하면 캐시는 `E/π`에 해당한다. 현재 PRTGI는 SH에 코사인 커널을 적용한 `E`를 저장하고 수신 단계에서 `ρ/π`를 곱한다. 연결 시 한쪽으로 통일해야 한다. 방향에 대해 일정한 radiance가 들어오는 반구에서 `E = πL`이 되는 GPU 해석 검사를 유지하고, π나 반사율을 두 번 적용하지 않는지 확인한다.

**바운스 의미.** 이전 프레임 캐시를 교차점의 간접광으로 다시 읽으면 반사 차수가 여러 프레임에 걸쳐 늘어난다. 현재의 명시적인 최대 6회 경로 추적과 같은 결과나 설정으로 표기할 수 없다. 6회 기준 이미지와 수렴 후 이미지의 차이뿐 아니라 가구 이동 직후의 지연·잔상·에너지 변화를 함께 측정해야 한다.

**화면 의존성과 절단.** 화면에서 부족한 표본을 생성하는 전략만 쓰면 미방문 영역의 표면 공급을 보장할 수 없다. 방 꾸미기에는 기존 에셋 로컬 준비 단계에서 기본 Surfel을 공급하고 화면 기반 생성을 보완용으로 사용하는 편이 적합하다는 판단이다. 셀 목록을 앞에서 일정 개수만 읽는 상한도 중요한 후보를 놓칠 수 있으므로 넘침과 후보 절단을 통계로 노출해야 한다.

**시간 필터와 변화 감지.** MSME는 변화에 빠르게 반응하기 위한 추정기이지 기하 변경의 무효화를 대신하지 않는다. 삭제된 가구의 Surfel을 즉시 제거하고, 이동 전후 주변 캐시의 신뢰도와 깊이 이력을 재설정해야 한다. 조명 버퍼는 이전/현재 프레임을 분리한다. 깊이 학습 버퍼도 이식 시 읽기·쓰기 순서를 분리해 결과가 GPU 실행 순서에 의존하지 않도록 설계한다.

## PC 우선 메모리 예산

[constants.ts](https://github.com/jure/webgiya/blob/0cd7f96859adc34e181f34a5d804e53fa94799cb/src/constants.ts)의 현재 기본 용량은 데스크톱 262,144개, 모바일 65,536개다. `surfelPool.ts`의 주요 배열만 계산하면 Surfel당 기하 32B + 조명/필터 이중 버퍼 160B + 방향 가중치 288B + 깊이 모멘트 256B = **736B**다. 따라서 풀의 이 네 배열만 각각 **184MiB / 46MiB**이고, 셀 목록의 할당식은 각각 약 **65MiB / 48.75MiB**를 추가한다. 이는 소스의 배열 크기를 합산한 값이며 실제 GPU 메모리 측정값이 아니다. BVH·재질·디버그·기타 버퍼는 포함하지 않았다.

모바일 기본값이 있다고 해서 현재 UE 프로젝트의 모바일 예산에 맞는다는 뜻은 아니다. PC에서는 작은 풀로 용량·캐시 적중률·업데이트 비용을 먼저 계측한다. 8×8 방향 유도 가중치와 4모멘트 깊이를 모두 처음부터 켜지 않고, 단계별로 품질 대비 비용을 확인한다. 모바일 예산과 포맷은 그 결과를 기준으로 별도로 정한다.

## 다음 구현 순서와 통과 조건

1. **에셋/인스턴스에 연결된 GPU Surfel 풀과 셀 인덱스.** 기존 에셋 준비에서 위치·법선·반경·반사율을 공급한다. 복제는 에셋 표본을 공유하고, 이동은 해당 인스턴스만 변환하며, 삭제는 소유 표본을 제거한다. 이동·회전·비균일 스케일·삭제·재삽입에서 오래된 표본이 남지 않고 셀 범위와 용량을 넘지 않는지 검증한다.
2. **GPU 조명 캐시의 반복 갱신.** 먼저 코사인 표본과 단순 시간 필터로 단위·수렴을 검증한다. 기존 삼각형 BVH와 최대 6회 경로 추적은 비교 경로로 유지한다. 계수 게시 과정의 CPU 읽기 비용과 새 캐시의 GPU 갱신 비용을 구분해 측정한다.
3. **조회용 방향별 가시성 캐시.** 현재 정확한 BVH 선분 검사와 비교하고, 미학습·기하 변경 영역은 정확한 경로로 복귀한다. 얇은 벽, 문틈, 구체 접촉부, 움직이는 가구 뒤의 빛샘을 별도 검사한다. 기존 정적 2모멘트 실험에서 얼룩이 늘었던 결과가 있으므로 자동으로 품질 향상을 가정하지 않는다.
4. **MSME·방향 유도·화면 보완 표본.** 앞 단계가 통과한 뒤 추가한다. 동일 광선 예산으로 오차와 광원 전환 응답을 비교한다. 방향 유도에서는 코사인/유도 혼합 PDF와 탐색 표본을 유지한다.

첫 단계는 기본 비활성 옵션으로 구현했다. 53개 인스턴스·18,312개 표본에서 이동·회전·음수/비균일 스케일·복제·삭제를 검사했고, GPU 풀과 공간 조회를 CPU 계산에 대조했다. 셀 목록은 표면 변경 시 전체 재구성하며 최종 조명에는 아직 사용하지 않는다. 다음 우선순위는 두 번째 단계다. 반해상도 옵션과 삼각형 BVH 조명은 비교 경로로 유지한다. Webgiya는 MIT 라이선스이며, 이후 코드를 이식하면 해당 저작권과 라이선스 고지를 함께 유지한다. 이번 표면 풀은 UE용으로 작성했으며 외부 코드를 복사하지 않았다.
