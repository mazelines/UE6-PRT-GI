# 동적 GI 전환: PC 기준 구현

작업 브랜치는 `feat/runtime-surfel-gi`이다. 목표는 **PC에서 동작·품질·갱신 비용을 검증한 뒤 모바일로 확장**하는 것이다. 방 꾸미기처럼 가구 배치가 달라지는 장면에서, 완성된 레벨의 광전달 행렬을 다시 굽지 않고 간접광을 갱신하는 경로를 먼저 만든다.

설계 기준은 사용자가 공유한 **Love and Deepspace GDC 2026 정리 문서**의 에셋별 표면 준비와 런타임 광전달 분리다. **삼각형 BVH 기반 GPU 경로 추적 기준 구현**과 선택적인 **Surfel irradiance 반복 갱신 경로**를 제공한다. 두 경로 모두 실제 광선 교차에는 삼각형 BVH를 사용한다. 디스크 Surfel 추적이나 Radiance Cascade 구현은 아니며, 문서에 나온 모바일 성능 수치를 이 코드에 적용해서도 안 된다.

## 현재 경로

1. `PRTGI.Runtime.Prepare`가 메시 LOD0와 재질 조합별 표면 데이터를 준비한다. 기존 재질 베이커를 에셋 로컬 공간에서 사용하고, 삼각형별 반사율·접선 공간 법선을 8×8 차트로 보관한다. 같은 메시와 재질을 쓰는 가구는 이를 공유한다. 현재 캐시는 메모리에만 있으며 에디터 세션마다 준비한다.
2. 0.25초 간격으로 메시·재질 식별자, 인스턴스 변환, 가시성, 그림자 설정, 광원, 프로브 배치를 확인한다. Static/Movable 메시와 ISM/HISM 인스턴스를 수집한다. `PRTGI.Ignore` 컴포넌트 태그로 제외할 수 있다.
3. 변경 시 현재 인스턴스 변환으로 삼각형 BVH를 만든다. 월드 공간 재질 차트는 메시·재질·변환별로 재사용하므로, 가구 하나를 움직일 때 다른 인스턴스의 차트를 다시 변환하지 않는다. 현재 장면에서 쓰지 않는 변환 캐시는 제거한다. 레벨 전체의 PRT 전송 항목을 생성하거나 저장하지 않는다. CPU 스냅숏 시간은 상태 로그에 별도로 기록한다.
4. GPU가 프로브에서 결정적인 구면 방향으로 광선을 쏘고, 충돌 표면에서 직접광을 평가한다. 이후 코사인 가중 반구 방향으로 경로를 이어 간접 반사를 계산한다. 기본 6회, 최대 12회이며, 처음 4회 이후 누적 반사율 최댓값이 0.01보다 작은 경로는 종료한다. 이는 편향된 근사다.
5. 입사 radiance를 SH9에 투영하고 각 밴드에 코사인 커널을 한 번 적용해 irradiance로 저장한다. 최종 수신 표면의 반사율/π 적용은 기존 resolve가 담당한다. 프로브 첫 교차의 뒷면 비율이 25%를 넘으면 해당 프로브를 제외한다.
6. GPU 작업은 프로브 단위 배치로 나눈다. 동시에 한 배치만 진행하며, 마지막에 SH를 CPU로 읽어 전체 세대 결과를 게시한다. 계산 도중 장면이 다시 바뀌면 이전 작업의 결과는 게시하지 않는다. 변경 시 기존 GI를 비우므로 새 결과가 완성될 때까지 간접광이 잠시 사라질 수 있다.
7. resolve의 프로브 가시성과 접촉 차폐에는 현재 BVH를 사용한다. 런타임 프로브의 이진 가시성은 차폐물을 하나 찾으면 탐색을 종료한다. 접촉 차폐에는 여전히 가장 가까운 교차 거리를 사용한다. 장면이 정지하면 광전달 갱신은 멈추지만, 화면 resolve와 가시성 검사 비용은 매 프레임 발생한다. 선택 옵션으로 동일 프레임의 반해상도 간접광을 재구성할 수 있다.

## 실행

UE6 Win64 Development Editor, DX12/SM6, 디퍼드 렌더링에서 사용한다. 레벨에 활성화된 `PRTProbeVolume`이 있어야 한다. 이 경로에서는 볼륨의 범위·간격을 사용하며 **Build Precomputation은 필요하지 않다**.

```text
PRTGI.Runtime.Prepare
PRTGI.SetMode PRT
r.PRTGI.Runtime 1
PRTGI.Runtime.Status
```

에셋 준비를 마친 메시·재질 조합은 이동·회전·크기 변경·복제·삭제 시 재준비하지 않는다. 새로운 메시나 재질 조합을 도입하거나 재질을 편집하면 `PRTGI.Runtime.Prepare`를 다시 실행한다. 아직 준비하지 않은 에셋은 상태의 `Error`로 알리고 GI 게시를 중단한다. 기존 정적 PRT로 돌아가려면 `r.PRTGI.Runtime 0`을 실행한다. 정적 경로에는 기존 사전 계산 캐시가 필요하다.

같은 에디터 프로세스에서 PIE로 들어갈 때는 준비한 에셋 데이터를 유지하고 월드의 조명 결과만 새로 계산한다. PIE 중 변환 변경은 게임 월드에 반영되며, PIE 종료 후에는 에디터 월드의 배치를 기준으로 다시 갱신한다.

| 설정·명령 | 기본값 / 의미 |
|---|---|
| `r.PRTGI.Runtime` | 0. 실험 경로는 명시적으로 활성화 |
| `r.PRTGI.Runtime.Rays` | 프로브당 256, 범위 64~1024 |
| `r.PRTGI.Runtime.Bounces` | 6, 범위 1~12 |
| `r.PRTGI.Runtime.ProbesPerBatch` | 32, 범위 1~256. GPU 시간 예산 자체는 아님 |
| `r.PRTGI.Runtime.VisibilityAnyHit` | 1. 런타임 프로브 차폐물을 찾으면 즉시 종료. 0은 가장 가까운 교차를 찾는 비교 경로 |
| `r.PRTGI.Runtime.ResolveHalfResolution` | 0. 1은 런타임 간접광을 가로·세로 절반 해상도로 계산하고 조건에 맞는 표면에서 재구성. 디버그 표시에는 적용하지 않음 |
| `PRTGI.Runtime.Status` | 에셋 준비 횟수, 세대, 폐기 작업, 변환 차트 갱신 수(`ChartUpdates`), CPU 스냅숏 시간, 게시 대기 여부, 수렴 시간 |
| `PRTGI.Runtime.Dump` | `Saved/PRTGIRuntime/probes.csv`에 게시된 SH와 유효성 기록 |
| `r.PRTGI.Runtime.SurfelPool` | 0. 1은 기준 조명과 함께 GPU 표면 풀·공간 인덱스를 갱신. 아직 조명 출력에 사용하지 않음 |
| `r.PRTGI.Runtime.SurfelSeedSpacingCm` | 50cm, 범위 1~1000. 에셋 로컬 삼각형 분할 기준. 변경 후 `PRTGI.Runtime.Prepare` 재실행 |
| `PRTGI.Runtime.Surfels.Validate` | GPU 풀·셀 목록·주변 조회를 CPU 계산과 대조. 결과는 상태 로그와 `Saved/PRTGIRuntime/surfel-audit.txt`에 기록 |
| `r.PRTGI.Runtime.SurfelCache` | 0. 1은 Surfel 조명 캐시로 프로브를 계산. 표면 풀도 자동 활성화 |
| `r.PRTGI.Runtime.CacheIterations` | 5, 범위 1~32. 전체 Surfel 집합을 갱신하는 횟수 |
| `r.PRTGI.Runtime.CacheRays` | 64, 범위 16~256. Surfel·반복당 코사인 표본 수 |
| `r.PRTGI.Runtime.CacheBatch` | 256, 범위 32~1024. 한 GPU 배치의 Surfel 수. ms 예산은 아님 |
| `r.PRTGI.Runtime.CacheBatchesPerSubmit` | 8, 범위 1~32. 한 번에 제출하는 캐시 배치 수. 반복 경계를 넘지 않음 |
| `r.PRTGI.Runtime.KeepLightingWhileUpdating` | 1. 캐시 경로에서 지오메트리·프로브 배치가 같으면 새 결과 게시 전까지 이전 SH 표시. 0은 즉시 제거 |
| `r.PRTGI.Runtime.CacheRelaxation` | 1, 범위 0.1~1. 새 반복값의 혼합 비율. 낮추면 수렴이 느려짐 |

`ConvergenceSeconds`는 여러 프레임에 걸친 전체 갱신 지연이다. GPU 패스 시간이나 프레임 시간과 구분한다. PC 기준 구현의 안전한 작업 크기 제한은 총 32,768 프로브와 100,000 삼각형이다. 제한을 넘기면 자동으로 해상도를 낮추지 않고 오류를 보고한다.

## PC 검증 결과 — 2026-11-03

UE6 Win64 Development Editor, DX12/SM6, RTX 4090, i9-14900KF에서 검증했다. Showcase의 전체 지오메트리 53개 인스턴스·11,400개 삼각형을 사용하고, 조명 계산은 ClassicBox의 512개 프로브로 제한했다. 프로브당 256개 광선, 최대 6회 반사, 배치당 32개 프로브이다. 수치는 개별 관측값이며 여러 번 반복한 성능 통계가 아니다. 원시 수치와 테스트 목록은 [검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_pc.json)에 있다.

화면 resolve 비용이 여전히 크다. 특히 현재 프레임의 BVH로 최대 64개 프로브의 가시성을 검사하는 경로는 모바일에 그대로 가져갈 수 없다. 후속 최적화에서는 이 기준 결과를 보존하고 런타임 프로브 가시성 캐시, 적은 보간 표본 수, 저해상도 resolve와 업샘플을 비교해야 한다. 최초 월드 구성과 새 고밀도 메시의 변환 비용도 별도로 측정해야 한다.

GPU 해석 검사는 `Automation RunTests PRTGI.Runtime.AnalyticHemisphere`로 실행한다. 전체 관련 검사는 `Automation RunTests PRTGI.`이다. 로컬 프로젝트의 기존 CommonUI 뷰포트 검사는 테스트 중에만 비활성화하고 복원했다. 엔진 전체나 EditorToolset 전체 테스트의 통과를 의미하지 않는다.

## 화면 합성 최적화 실험 — 2026-11-03

`r.PRTGI.Runtime.ResolveHalfResolution 1`은 프로브 보간과 BVH 가시성 검사를 가로·세로 절반 해상도에서 수행한다. 최종 픽셀은 주변 네 표본이 같은 볼륨에 속하고, 법선 내적이 0.9995 이상이며, 두 접평면의 오차가 0.1cm 이하이고, 표본 간 거리가 최소 프로브 간격의 10% 이내일 때만 보간한다. 하나라도 조건을 벗어나면 그 픽셀에서 원래 해상도로 다시 계산한다. 선택 볼륨의 간접광만 재구성하며, 겹치는 볼륨의 경계 블렌딩은 기존 계산을 유지한다.

재질 색상·금속성·GGX 에너지 보정과 접촉 차폐는 기존 최종 픽셀에서 적용한다. 조명 버퍼는 노출 적용 전 FP32 irradiance를 저장해 밝은 광원에서 FP16 범위를 넘는 문제를 피한다. 이전 프레임의 버퍼를 사용하지 않는다. 3309×1508에서는 추가 임시 버퍼가 약 19.0MiB 필요하다. 이는 프로브 가시성 캐시나 Radiance Cascade가 아니라 화면 합성 단계의 공간적 근사다.

RTX 4090 / i9-14900KF, UE6 Win64 Development Editor, DX12/SM6에서 세 모드를 번갈아 5회 측정했다. 에디터 화면 비율은 100%, 뷰포트는 3309×1508, AA와 접촉 차폐는 끄고 간접광만 표시했다. ClassicBox·ColorBox 두 볼륨의 1,664개 프로브, 전체 11,400개 삼각형, 프로브당 256광선·최대 6바운스다. 아래 시간은 광전달 갱신이 끝난 뒤 **화면 합성 패스 합계의 중앙값**이며 전체 프레임 시간이나 광전달 갱신 시간이 아니다.

| 시점 | 가장 가까운 교차 / 전체 해상도 | 첫 차폐물 종료 / 전체 해상도 | 첫 차폐물 종료 / 반해상도 |
|---|---:|---:|---:|
| 원경 | 7.119ms | 7.127ms | 8.865ms |
| 구체 근접 | 57.970ms | 53.614ms | 18.151ms |

근접 화면에서는 반해상도가 기준 대비 약 69% 빨랐지만 원경에서는 약 25% 느렸다. 따라서 **반해상도 기본값은 0을 유지**한다. 첫 차폐물 종료도 모든 시점에서 성능 이득을 보장하지 않는다. 카메라와 표면 구성에 따른 비용 차이가 크므로 이 수치를 게임 전체의 성능으로 일반화하지 않는다. 이전 절의 측정은 볼륨 수·화면 비율·접촉 차폐 조건이 달라 직접 비교할 수 없다.

1399×789의 홀수 해상도에서 선형 HDR을 비교했다. 첫 차폐물 종료는 원경·구체 근접에서 기준 캡처와 픽셀 차이가 0이었다. 반해상도의 전체 화면 RGB 상대 RMSE는 각각 약 0.164%, 0.215%였다. 같은 기준 경로의 반복 캡처에도 각각 약 0.052%, 0.131% 차이가 있으므로 작은 차이 전부를 이 변경의 오차로 해석하지 않는다. 전체 화면 수치는 국소 윤곽선의 오차 상한을 의미하지 않는다. 구체를 25cm 이동한 상태와 접촉 광선 8개를 켠 상태도 별도로 비교했다. 원시 측정·카메라·설정·검증 목록은 [합성 검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_resolve.json)에 기록했다.

## GPU Surfel 풀과 공간 조회 — 2026-11-03

Webgiya 검토 후 첫 단계로 **에셋 표본 공유와 인스턴스별 GPU 표면 관리**를 추가했다. 표면 풀에는 위치·법선·반사율·소유권을 저장한다. `SurfelPool`만 켜면 조명은 기존 기준 경로에서 계산한다. 후속 조명 캐시는 아래의 별도 `SurfelCache` 옵션으로 선택한다.

```text
PRTGI.Runtime.Prepare
PRTGI.SetMode PRT
r.PRTGI.Runtime 1
r.PRTGI.Runtime.SurfelPool 1
PRTGI.Runtime.Status
PRTGI.Runtime.Surfels.Validate
```

활성화된 유효 `PRTProbeVolume`이 필요하다. `SurfelError`가 비어 있고 `SurfelLive`가 생성됐는지 확인한 뒤 검사를 실행한다. 검사는 요청할 때만 전체 GPU 데이터를 읽는다. `SurfelAudit=PASS`의 `Revision`은 요청 당시의 스냅숏이며 `CurrentRevision`과 다르면 그 사이 장면이 갱신된 것이다. `SurfelUpdated`와 `SurfelRetired`는 마지막 표면 변경에서 갱신·반환한 인스턴스 범위 수다. 정지 중에는 마지막 수치를 유지한다.

### 표본 생성과 소유권

각 삼각형을 최장 변과 로컬 간격에 따라 균등 분할하고, 작은 삼각형마다 중심 표본 하나를 만든다. 기존 8×8 재질 차트에서 반사율과 셰이딩 법선을 읽는다. 로컬 표본은 위치·셰이딩 법선·중심 상대 꼭짓점 두 개·반사율·기하 법선의 6개 `float4`, 즉 96B다. 같은 메시·재질 조합을 사용하는 인스턴스가 공유한다. 세 번째 상대 꼭짓점은 앞의 두 벡터 합의 음수로 복원한다.

월드 풀은 표본당 64B다. GPU에서 인스턴스 변환과 역전치 법선 변환을 적용하고, 변환된 꼭짓점을 포함하는 지지 구의 반경을 계산한다. 음수·비균일 스케일을 지원하지만 밀도는 에셋 로컬 기준이므로 확대하면 월드 표본 간격도 커진다. 월드 밀도에 따른 재분할이나 LOD는 아직 없다. 현재 조회는 지지 구 포함 검사이며 디스크 교차나 조명 보간 가중치가 아니다.

컴포넌트는 UObject 생성 일련번호를 포함한 `FObjectKey`로 구분한다. ISM/HISM은 UE의 `FSMInstanceElementIdMap`을 함께 사용해 앞쪽 인스턴스 삭제로 배열 번호가 바뀌어도 남은 인스턴스의 소유권을 유지한다. 움직인 인스턴스의 슬롯 범위만 변환하고, 삭제된 범위는 0으로 지운 뒤 반환한다. 복제는 로컬 에셋 버퍼를 공유하면서 새 슬롯 범위를 받는다. 풀 비활성화나 월드 전환 시 월드 풀은 다시 구성한다.

기본 용량은 65,536개, 해시 버킷은 16,384개다. 풀 4MiB, 셀 키 1MiB, 슬롯 목록 0.25MiB, 오프셋 약 0.0625MiB로 **주요 상주 버퍼 합계 약 5.31MiB**다. 에셋 로컬 버퍼, 임시 스캔 버퍼, 감사용 읽기 버퍼는 제외한 배열 크기 합계이며 GPU 메모리 실측값이 아니다. 연속 슬롯 할당이므로 빈 슬롯 합계가 충분해도 단편화로 실패할 수 있다. 용량 초과·잘못된 변환·지원 범위 초과는 `SurfelError`로 보고하고 직전 유효 풀을 보존한다. 오류 상태의 풀은 현재 장면과 일치한다고 간주하면 안 된다.

### 공간 인덱스와 검증

기본 셀 폭은 32cm다. 표본 반경의 두 배를 담는 레벨을 16단계 중 선택하고, 중심을 해당 레벨의 셀 하나에 넣는다. GPU에서 **개수 계산 → 블록별 누적 합 → 블록 오프셋 합산 → 슬롯 배치** 순서로 버킷별 연속 목록을 만든다. 해시 충돌은 정확한 정수 셀 좌표와 레벨을 다시 비교해 제외한다. 셀마다 앞의 몇 개만 읽는 절단은 없다. 검증용 조회는 각 레벨의 주변 27개 셀을 확인한다. 이는 정확성 비교용이며 최종 화면 합성에 맞춰 최적화한 조회가 아니다.

지오메트리가 바뀌면 셀 목록 전체를 다시 만든다. 광원만 바뀌거나 변환이 같으면 표면 풀 세대를 올리지 않는다. CPU 소유권 대조와 전체 셀 재구성 비용은 후속 최적화 대상이다. 현재 월드 좌표는 각 축 ±200,000m, 지지 반경은 기본 셀 폭의 16,384배 이내로 제한한다. 삼각형 한 변의 분할 수는 최대 32, 에셋 표본은 최대 1,048,576개이며 풀 용량 제한은 별도로 적용된다.

## GPU 조명 캐시 반복 갱신 — 2026-11-03

`r.PRTGI.Runtime.SurfelCache 1`을 켜면 Surfel의 간접 irradiance를 GPU에서 반복 갱신한 뒤 프로브 SH로 투영한다. **기본값은 0**이다. 이번 단계는 단위·수렴·장면 변경 처리를 검증한 첫 통합이며, 기존 경로보다 빠르거나 정확하다는 의미는 아니다.

```text
PRTGI.Runtime.Prepare
PRTGI.SetMode PRT
r.PRTGI.Runtime 1
r.PRTGI.Runtime.SurfelCache 1
PRTGI.Runtime.Status
PRTGI.Runtime.Dump
```

`Pending=0 CacheRetained=1`이고 `Published`가 활성 볼륨 수와 같으면 현재 세대의 계산·게시가 완료되고 최종 캐시를 GPU에 유지하는 상태다. 계산 중에는 `CacheSweep`, `CacheOffset`, `CachePhase`로 진행 상황을 확인한다. `CachePhase=0`인 채 `Pending=1`이면 프로브 투영 단계다. `SurfelCache 0`으로 돌아가면 기존 BVH 다중 바운스 경로를 다시 계산한다. 캐시 옵션이 켜진 동안 `SurfelPool 0`만으로 표면 풀을 끌 수는 없다.

### 계산과 조회

캐시 `I(x)`는 수신 표면의 반사율을 적용하기 전 **간접 irradiance E**다. 초기값은 0이다. Surfel 법선의 코사인 분포로 광선을 쏘고, BVH 교차점 `y`에서 다음 값을 평균한다.

```text
J(x) = average[ rho(y) * (E_direct(y) + I_previous(y)) ]
I_next(x) = (1 - alpha) * I_previous(x) + alpha * J(x)
```

코사인 PDF 적분의 π와 교차 표면의 Lambert `1/π`가 상쇄된 식이다. 교차 실패·뒷면 교차는 0이다. 실제 레벨의 하늘광·발광은 여전히 지원하지 않는다. 자동화 검사의 일정한 환경 radiance는 해석적 검증용 입력이며 레벨 설정에 연결하지 않았다.

각 에셋 삼각형에 표본 시작 번호와 분할 수를 저장하고, 월드 BVH 정렬 후에도 해당 인스턴스의 GPU 슬롯 범위와 연결한다. 교차점에서는 그 삼각형의 barycentric 격자 주변 표본만 compact 가중치로 보간한다. 다른 벽이나 다른 인스턴스의 가까운 표본은 섞지 않는다. 1단계 공간 해시 전체를 광선마다 검색하지 않으며, 현재 조명 조회는 삼각형 연결을 사용한다. 삼각형 경계 사이의 연속성과 표본 밀도에 따른 오차는 남아 있다.

이전·현재 irradiance 버퍼를 분리한 Jacobi 반복이다. 한 바퀴의 모든 배치가 같은 이전 버퍼를 읽고, 전체 Surfel 갱신이 끝나야 교환한다. 고정된 표본 방향을 사용하므로 반복 순서나 배치 크기로 결과가 달라지지 않는다. `CacheRelaxation`은 반복을 완화하는 계수이며, 프레임마다 새로운 표본을 누적하는 시간 필터나 MSME가 아니다.

기본 5회 갱신과 마지막 프로브 광선의 표면 교차를 합치면, `alpha=1`에서 최대 6개 반사 표면까지 기여한다. 캐시 경로의 반사 깊이는 `CacheIterations`가 결정하며 `Runtime.Bounces`는 기준 경로의 설정이다. 공간 보간·다른 표본 집합을 사용하고 기준 경로의 throughput 조기 종료를 적용하지 않으므로 두 결과가 같지는 않다. `alpha<1`에서는 반복 횟수를 바운스 수로 해석하지 않는다. 반복 수를 늘려 변화가 작아지는 것은 공간 근사 오차까지 사라진다는 뜻이 아니다.

마지막 프로브 광선은 교차점에서 `rho * (E_direct + I) / π`를 평가하고 기존 SH9 투영·코사인 커널을 적용한다. 화면은 기존 프로브 resolve와 BVH 가시성을 사용한다. 화면 픽셀에서 Surfel 조명 캐시를 직접 조회하는 경로는 아직 없다.

### 세대와 메모리 수명

배치·재질 준비·광원·관련 설정이 바뀌면 전체 조명 캐시를 0부터 계산한다. 표면 풀의 세대와 조명 세대는 별개라 광원 변경에는 표면 표본 재변환이 필요 없다. 계산 시작 시 GPU 표면 풀의 불변 스냅숏을 복사하므로, 도중에 가구가 움직여도 이전 BVH와 새 Surfel 위치가 섞이지 않는다. 바뀐 세대의 결과는 게시하지 않는다.

캐시 전체와 프로브가 완성되면 한꺼번에 게시한다. 2026-11-04부터 지오메트리·프로브 배치가 같은 캐시 갱신은 이전 SH를 표시한 채 진행한다. 가구 이동·추가·삭제, 프로브 배치 변경, 경로 전환 및 오류에서는 이전 결과를 제거한다. **가구를 움직일 때는 계산 중 간접광 공백이 남으며, 계속 움직이면 게시가 지연될 수 있다.** 광선 캐시의 지역 무효화는 아래 옵션으로 추가했지만, irradiance의 지역 갱신과 점진적 게시는 후속 과제다. 장면이 멈추고 지정된 반복이 끝나면 갱신을 멈추며, 매 프레임 5회 바운스를 다시 계산하지 않는다.

65,536개 용량에서 표면 스냅숏 4MiB와 irradiance 이중 버퍼 2MiB가 계산 중 추가된다. 완료 후 최종 irradiance 1MiB와 스냅숏 4MiB를 유지하고, 반대쪽 irradiance 및 계산용 BVH·재질·광원·프로브 버퍼를 해제한다. 표면 풀, 로컬 에셋, 삼각형 연결, 활성 슬롯, 화면 resolve 자원은 별도다. 일반 실행에서는 Surfel irradiance 전체를 CPU로 읽지 않는다. 2026-11-04부터 중간 완료 확인은 GPU fence를 사용하며, 최종 프로브 SH 읽기만 남아 있다.

새 `PRTGI.Runtime.SurfelCacheAnalytic` 검사는 `E=πL`, 두 단계 반사 전달, `rho/π`의 단일 적용, 완화 반복의 해석적 수렴, 배치 경계 독립성, 비활성 슬롯 초기화, 조명 초기화 후 0 출력을 검사한다. 전체 PRTGI 자동화 19개가 통과했다. 삼각형별 보간 오차, 장시간 움직임, 빛샘, 화면 잔상 및 모바일 성능은 후속 검증 대상이다.

## GPU 제출과 조명 게시 개선 — 2026-11-04

배치마다 16B 완료 데이터를 CPU로 읽던 경로를 **GPU fence 확인**으로 바꿨다. 캐시 배치는 기본 8개씩 하나의 RDG 그래프에 제출한다. 동시에 진행 중인 제출은 하나로 제한하며, 하나의 반복에 남은 배치만 묶는다. 모든 배치가 같은 이전 irradiance를 읽고 서로 다른 슬롯 범위를 쓴다. 전체 Surfel 갱신이 끝나야 이중 버퍼를 교환하므로 Jacobi 결과는 바뀌지 않는다. 마지막 프로브 SH는 기존처럼 한 번 CPU로 읽는다.

18,312개 Surfel, 배치당 256개, 반복 5회에서는 캐시 배치 360개를 45회 제출로 묶는다. 프로브 512개를 32개씩 처리하는 16회를 합하면 총 제출은 376회에서 61회로 줄어든다. `CacheBatchesPerSubmit=1`은 비교용이며 중간 완료 확인에는 이 경우에도 새 GPU fence를 사용한다. 묶음 수는 고정 작업량 제어이고 GPU 시간 예산은 아니다.

광원 변경 중 조명이 완전히 사라지던 구간도 줄였다. 지오메트리·재질 식별자·프로브 배치의 서명을 조명 세대와 별도로 기록하고, 이미 게시된 캐시 결과와 일치하면 이전 SH를 유지한다. 이때 상태는 `Pending=1 Published>0 HoldingLighting=1`이다. 새 결과가 완료되면 목록을 교체하므로 볼륨을 중복 추가하지 않는다. 최종 결과의 내용과 게시 시점은 그대로이며 보간 전환은 없다. **이전 조명을 표시하는 동안 새 광원에 대한 반응은 지연된다.** 이전 irradiance로 계산을 시작하는 warm start나 지역 갱신도 아니다. 가구·프로브 배치가 달라지거나 오류가 발생하면 이전 SH를 지운다.

RTX 4090 / i9-14900KF, UE6 Development Editor·DX12/SM6, ClassicBox 512개 프로브, 전체 Showcase 18,312개 Surfel에서 1→4→8 묶음을 세 차례 반복했다. 광원 밝기를 50,000/100,000으로 번갈아 바꿨고 다른 계산 설정은 동일하다. 아래는 변경 감지 후 세대 계산 시작부터 완성 결과 게시까지의 시간이다. 최대 0.25초의 장면 변경 감지 대기는 포함하지 않는다.

| 한 번에 제출할 배치 | 게시 지연 3회 | 중앙값 |
|---|---|---:|
| 1 | 6.505 / 6.491 / 6.444초 | 6.491초 |
| 4 | 1.985 / 1.868 / 1.917초 | 1.917초 |
| 8 (기본) | 1.342 / 1.272 / 1.299초 | 1.299초 |

8개 묶음은 이 조건에서 중앙값 기준 약 **80% 짧아졌다**. 완료 확인만 fence로 바꾼 1개 묶음은 이전 지연과 비슷하므로, 이 측정의 주된 개선은 묶음 제출에 있다. 전체 프레임 속도가 5배가 됐다는 의미는 아니다.

별도의 ProfileGPU 검사에서는 캡처 구간을 확보하려고 반복 수를 32로 늘리고, 갱신 패스가 관측된 프레임 네 개씩을 비교했다. 배치당 표본·광선 수는 위와 같다. 캐시 갱신 패스 합계는 1개 묶음에서 **0.303~0.355ms**, 8개에서 **2.177~2.677ms**였다. resolve·렌더링 전체 및 CPU 시간은 제외했다. 일부 캡처 프레임에는 완료 대기 중이라 캐시 패스가 없었다. 묶음을 키우면 갱신이 실행되는 프레임의 GPU 부담은 커진다. 큰 장면이나 느린 GPU에서는 묶음 수를 낮춰야 하며, 모바일 예산을 충족했다는 검증은 아니다.

검증 결과는 다음과 같다. [원시 상태·측정·검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_scheduling.json)에 조건을 기록했다.

- 모든 묶음의 최종 SH가 같은 광원 밝기의 기존 결과와 바이트 단위로 일치했다. 기존 기준 경로 대비 약 10.5%의 공간 근사 차이는 그대로다.
- 광원 갱신 중 게시된 SH가 직전 결과와 정확히 일치하고, 완성 후 새 결과로 교체됐다. 가구 이동과 유지 옵션 비활성화에서는 `Published=0`으로 즉시 제거됐다.
- 진행 중인 장기 계산을 취소한 뒤 새 세대 결과, PIE, 원래 배치 복원, 기준 경로 복귀를 확인했다.
- GPU 해석 검사를 묶음 1·2·8 및 반복 끝의 잔여 배치까지 확장했고, 전체 PRTGI 자동화 19개가 통과했다.

### 방 하나와 GI 볼륨 하나를 사용할 때

기본 전체 레벨 모드에서 GI 볼륨은 **프로브 배치와 수신 영역**을 정의하며, 참여 지오메트리를 그 경계 안으로 제한하지 않는다. 위 측정도 ClassicBox 볼륨 하나만 켰지만 레벨 전체 53개 인스턴스·18,312개 Surfel을 계산했다. 따라서 1.299초는 독립된 방 하나만 계산한 결과가 아니다. 2026-11-04 점검 당시 Showcase에는 전면 ClassicBox·ColorBox·ShinyBox 외에 Global·MetallicBox·InvertedBox를 포함한 6개 볼륨 액터가 있었다.

2026-11-04에 선택적 **방별 참여 메시·조명 캐시·작업 상태 분리**를 추가했다. `r.PRTGI.Runtime.Rooms=1`에서 활성 볼륨 하나가 독립 작업 하나를 소유한다. 기본값은 0이므로 기존 레벨은 전체 레벨 방식으로 동작한다. 방 모드는 런타임 기준 경로와 Surfel 조명 캐시 모두에 적용되며, 정적 PRT 사전 계산에는 적용되지 않는다.

볼륨 경계로 메시를 자르지 않는다. 각 볼륨의 Details → **PRT → Runtime Room**에서 `Runtime Included Actors`에 액터를 지정하거나 `Runtime Participant Tags`에 액터/컴포넌트 태그를 지정한다. 두 조건은 합집합이다. 공유 벽과 외부 차폐물은 필요한 모든 방에 포함한다. 기존 `PRTGI.Ignore` 컴포넌트 태그, 숨김 및 가시성 제외는 그대로 적용하며, ISM/HISM은 컴포넌트 전체가 참여한다. 참여 목록이 비었거나 유효한 메시가 하나도 없으면 해당 방의 결과를 제거하고 오류를 표시한다. 전체 레벨로 자동 전환하지 않는다.

```text
PRTGI.Runtime.Prepare
r.PRTGI.Runtime.SurfelCache 1
r.PRTGI.Runtime.Rooms 1
r.PRTGI.Runtime 1
PRTGI.Runtime.Status
PRTGI.Runtime.Dump
```

`Prepare`는 여전히 전체 레벨의 메시/재질 변형을 준비한다. 방 작업들은 이 CPU 로컬 차트·Surfel 표본을 공유하지만, 월드 BVH·표면 풀·irradiance·프로브 SH는 각각 소유한다. 공유 벽의 GPU 데이터도 방마다 존재한다. 방별 풀은 필요한 표본 수를 기준으로 256~65,536 사이의 2의 거듭제곱 용량을 할당하고 증가할 때 확장한다. 사용량이 줄었다고 즉시 축소하지는 않는다.

가구의 변환·추가·삭제와 참여 목록의 실질적인 변경은 그 메시를 포함한 방만 무효화한다. 공유 메시 변경은 포함한 방 모두에 전파된다. 현재 모든 지원 광원은 각 방의 입력이므로 **광원 변경은 모든 방을 갱신**한다. 변경된 방에서는 전체 BVH와 조명 캐시를 다시 계산하고, 지오메트리가 바뀌면 그 방의 이전 SH를 제거한다. 다른 방의 게시 결과는 유지된다. 방 내부의 작은 영역만 갱신하는 기능이나 방 사이 광 전달은 아직 없다.

각 방이 매 프레임 묶음 제출을 하나씩 실행하지 않도록 공통 스케줄러가 제출 권한을 순환 배분한다. 정상 작업에서는 진행 중인 조명 제출이 하나이며, 권한이 없는 방도 완료 확인은 수행한다. 이미 제출된 작업은 취소 요청 후에도 GPU에서 끝날 수 있지만 그 결과는 게시하지 않는다. 표면 풀 갱신·스냅샷 복사·화면 resolve는 이 조명 제출 예산과 별개다. 따라서 GPU 밀리초 상한을 보장하지 않는다.

화면의 프로브 가시성과 접촉 감쇠도 선택한 볼륨의 BVH를 사용한다. 렌더러는 서로 다른 BVH를 하나의 버퍼에 모으고 볼륨별 노드·삼각형 오프셋으로 조회한다. 같은 BVH를 공유하는 기존 전체 레벨 모드에서는 버퍼를 중복 적재하지 않는다. `Runtime.Status`는 액터 경로별 세대·대기·게시 상태를 출력하고, `Runtime.Dump`는 `probes.csv`와 함께 볼륨 인덱스·GUID·경로를 연결하는 `Saved/PRTGIRuntime/rooms.tsv`를 기록한다. 비활성화된 방은 인덱스에서 빠지므로 비교할 때 이 매핑을 사용한다.

## 반복 광선 추적 재사용 — 2026-11-04

`r.PRTGI.Runtime.ReuseTransport=1`은 하나의 조명 갱신 안에서 바뀌지 않는 교차·차폐 계산을 재사용한다. 기본값은 0이다. 방별 작업 분리 다음 단계로, 변경된 방을 다시 계산하는 GPU 비용을 줄인다. **이 옵션 단독으로는 이전 조명 세대를 재사용하지 않는다.** 거리만으로 갱신 범위를 자르면 멀리 떨어진 차폐 영향과 다중 반사를 놓칠 수 있어, 먼저 같은 결과를 유지하는 반복 계산부터 줄였다. 이후 추가한 `RegionalTransport` 옵션의 갱신 간 재사용은 다음 절에서 설명한다.

기존 캐시 경로는 모든 Jacobi 반복에서 같은 Surfel 위치·법선과 같은 난수 시드로 광선을 생성했다. 지오메트리와 조명은 갱신 작업의 불변 스냅샷이므로, 각 광선이 만나는 삼각형·barycentric 좌표와 교차점의 직접광은 반복 사이에 변하지 않는다. 새 경로는 첫 반복에서 다음 정보를 GPU에 기록한다.

| 기록 | 내용 |
|---|---|
| 첫 번째 `float4` | 직접 irradiance RGB, 삼각형 인덱스 |
| 두 번째 `float4` | barycentric 좌표 2개, 예약 필드 2개 |

교차하지 않은 광선과 뒷면·잘못된 반구로 향한 광선도 반드시 기록한다. 실제 레벨에서 교차 실패의 기여는 0이며, 해석 테스트의 환경 radiance만 별도 값을 사용한다. 인덱스는 희소한 Surfel 슬롯 대신 현재 활성 표본 순서와 광선 번호로 계산한다. 표본 방향과 교차 좌표를 양자화하지 않는다.

두 번째 반복부터는 저장한 교차 위치에서 재질과 **이전 반복의 irradiance**를 읽고 기존 식 `rho * (E_direct + I_previous)`를 평가한다. 지오메트리 추적과 광원 차폐 추적은 건너뛰지만, 간접광을 갱신하는 이중 버퍼 Jacobi 반복은 그대로 실행한다. 프로브 SH 투영은 기존 경로를 사용한다. 묶음 제출 수, 프로브 배치 수, 완료 확인과 게시 시점의 규칙도 유지한다.

가구·재질·광원·참여 목록이나 계산 설정이 바뀌면 새 작업이 첫 반복부터 다시 기록한다. 진행 중인 이전 작업의 결과는 폐기한다. 갱신 중 이전 SH 표시와 방별 무효화 규칙은 그대로다. 이 표는 디스크에 저장하는 PRT 사전 계산 데이터가 아니며, 작업 완료 후 임시 GPU 자원과 함께 해제한다.

```text
r.PRTGI.Runtime.SurfelCache 1
r.PRTGI.Runtime.ReuseTransport 1
r.PRTGI.Runtime.TransportBudgetMB 64
PRTGI.Runtime.Status
```

에셋 준비와 런타임 GI 활성화는 앞 절과 같다. `TransportBudgetMB`는 **방/작업 하나당** 추가 메모리 예산이며 기본 64MiB, 범위는 0~512다. 전체 활성 Surfel 수 × 캐시 광선 수 × 32바이트가 이 예산을 넘거나 반복이 1회이면 표를 만들지 않고 기존 방식으로 계산한다. 작업별 예산이므로 동시에 여러 방을 갱신하면 합계는 이를 넘을 수 있다. 예산 0은 재사용 없이 결과를 비교하는 데 사용할 수 있다.

상태의 `TransportReuse`는 해당 작업이 실제로 재사용을 선택했는지를 나타낸다. `TransportBytes`는 사용한 표의 할당 크기이고, `TransportRetained=0`은 완료 후 해제를 요청한 상태다. 완료 기록에 크기가 남아 있어도 그 표를 다음 세대에 재사용하지 않는다. 원래의 표면 풀·irradiance·BVH·프로브 메모리는 이 수치에 포함되지 않는다.

## 가구 이동 시 광선 캐시의 지역 무효화 — 2026-11-04

`r.PRTGI.Runtime.RegionalTransport=1`은 완료된 광선 표를 다음 갱신까지 보관하고, **위치·회전이 바뀐 가구의 영향을 받을 수 있는 광선만 다시 추적**하는 실험이다. 기본값은 0이며, 켜면 `ReuseTransport` 경로도 사용한다. 이 옵션만 사용하면 간접광 캐시와 프로브 SH는 변경된 방 전체에서 0부터 계산한다. 아래의 `RegionalIrradiance`와 `ProgressiveProbes`는 각각 반복별 결과 재사용과 부분 게시를 추가하는 별도 옵션이다.

CPU는 마지막으로 완료된 작업의 참여 인스턴스와 새 작업을 비교한다. 참여 대상·재질 키·그림자 설정·광원·광선 수가 같고 표면 슬롯이 유지된 경우에만 재사용 후보가 된다. 변경된 인스턴스의 이전/현재 월드 AABB를 합치고 부동소수점 위치 오차를 고려해 확장한다. 메모리 예산, 참가자 변경, 크기 변경, 이전 작업 미완료 등의 조건에서는 전체 추적으로 복귀한다. 비균일 크기 변경은 초기 검증에서 엄격한 비교 기준을 통과하지 못했으므로 현재 모든 크기 변경을 전체 추적으로 제한한다.

첫 반복에서 GPU가 각 광선을 다음 순서로 검사한다.

1. 출발 Surfel의 위치·법선이 달라졌으면 다시 추적한다.
2. 출발점부터 기존 첫 교차점까지의 선분이 변경 영역을 지나면 다시 추적한다. 교차 실패는 기존 64m 추적 길이를 사용한다.
3. 기존 교차점에서 각 광원으로 향하는 그림자 광선이 변경 영역을 지나면 다시 추적한다. 현재 가려진 광선도 검사하므로 멀리 이동한 차폐물이 만드는 변화도 대상이 된다.
4. 거의 같은 거리에 여러 삼각형이 교차한 경우에는 BVH 재정렬의 영향을 받을 수 있어 다시 추적한다.
5. 나머지는 기존 교차·직접광 결과를 복사한다. BVH 정렬로 달라진 삼각형 번호는 Surfel 소유자와 로컬 삼각형 슬롯을 기준으로 변환한다.

새 표를 이용한 Jacobi 반복은 기존과 같다. 단순히 가구 주변 반경만 갱신하는 방식이 아니며, 변경 영역의 합집합이 크면 재사용 비율이 낮아진다. 계속 움직여 이전 갱신이 끝나지 않은 경우에는 미완료 표를 재사용하지 않는다.

이 모드의 표는 광선당 **48바이트**다. 기존 32바이트에 첫 교차 거리·교차 중복 표시·그림자 광선 시작점을 보관한다. 완료 후에도 표를 유지하며, 새 작업에서는 이전 표와 새 표의 합계를 작업별 `TransportBudgetMB`와 비교한다. 예산을 넘으면 이전 표를 사용하지 않는다. 새 표 하나도 예산을 넘으면 기존 반복 추적 방식으로 돌아간다. 기본 세 방의 표 크기는 ClassicBox 약 7.95MiB, ColorBox 16.31MiB, ShinyBox 16.07MiB다. 표면 스냅샷·irradiance 등 다른 자원은 별도이며, 이것은 전체 GPU 메모리 상한이 아니다.

상태의 `RegionalReuse=1`은 이전 세대의 표를 사용하는 작업이다. `QueriesReused`와 `QueriesRebuilt`는 첫 반복에서 재사용/다시 계산한 광선 항목 수다. 이 값으로 그림자 추적 호출 수나 프레임 속도 향상을 직접 환산할 수는 없다. `TransportRetained=1`은 완료 후에도 표를 보관하는 정상 상태다.

### 직접 실행 가능한 검증 설정

검증용 맵 **`/Game/Tests/PRTGI_RegionalValidation`**을 추가했다. 원래 Showcase를 복사하고 ClassicBox·ColorBox·ShinyBox만 활성화했다. 참여 메시 수는 각각 15·14·14개이며, 각 방의 메시와 공통 `Environment_` 메시 5개를 포함한다. 원래 Showcase의 작업 파일과 사전 계산 캐시는 이 변경에 포함하지 않는다.

맵을 연 다음 UE Python 콘솔에서 아래 스크립트를 실행하면 에셋 준비와 모든 런타임 설정을 적용한다. 스크립트는 검증 맵에서만 실행되며 맵을 저장하지 않는다.

```python
exec(open(unreal.Paths.project_dir() + "Plugins/PRTGI/Tools/setup_regional_validation.py", encoding="utf-8").read())
```

설정은 방 모드·Surfel 캐시·반복 추적 재사용·지역 무효화·이동 중 조명 유지·지역 irradiance·프로브 부분 게시를 켠다. 광선 표 예산 64MiB/방과 irradiance 이력 예산 16MiB/방, 캐시 5회·64 rays·256개 배치·8개 묶음, 프로브 256 rays·32개 배치를 사용한다. 이 설정은 프로젝트 전체의 기본값을 변경하지 않는다. 스크립트 실행 후 세 방의 `Pending=0 Published=1`을 확인하고 `Classic_Box_Small_Cube`를 옮기면 된다. `PRTGI.Runtime.Status`와 `PRTGI.Runtime.Dump`로 상태와 SH를 확인한다. 원상태 복원은 테스트 맵을 저장하지 않고 다시 여는 방식으로 수행한다.

전체 추적 비교와 그림자 선분 검사, 메모리 예산 초과, 크기·광원 변경의 복귀 동작은 [검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_regional.json)에 기록한다. UE6 최종 빌드와 PRTGI 자동화 19개가 통과했다. ClassicBox의 작은 상자를 X축으로 40cm 이동했을 때 173,568개 중 161,588개(93.10%)의 광선 항목을 재사용했고, 다른 두 방의 세대와 SH는 변하지 않았다. 이동·회전의 해당 방 상대 L2 오차는 각각 약 `8.92e-9`, `1.43e-8`로, 방별 상대 L2와 정규화 최대 오차를 모두 `1e-6` 미만으로 검사한 기준을 통과했다. 크기·광원 변경과 8MiB 예산 복귀 결과는 비교 CSV가 일치했다.

이 경로는 비트 단위 일치를 보장하지 않는다. 비교는 덤프된 CSV의 프로브 유효성과 방별 SH를 사용하며, 재사용 비율을 프레임 속도 향상률로 해석해서는 안 된다. 모바일 메모리·대역폭 및 연속 이동 중 품질은 후속 검증 대상이다.

## 갱신 중 이전 조명 유지 — 2026-11-05

`r.PRTGI.Runtime.KeepLightingOnGeometryChange=1`은 프로브 배치가 같은 가구 이동·추가·삭제 중에도 기존 SH를 표시한다. `KeepLightingWhileUpdating=1`과 Surfel 캐시가 필요하며 기본값은 0이다. 화면 합성에는 새 BVH를 즉시 연결하고, 변경된 인스턴스의 이전·현재 경계 안에 들어간 프로브는 제외한다. 연속 이동으로 계산이 취소되면 제외한 프로브를 누적 유지하고, 새 계산이 완료되면 새 유효성과 SH로 교체한다. 프로브 배치나 볼륨 선택 조건이 바뀌면 이전 조명을 유지하지 않는다.

UE6 빌드와 자동화 20개가 통과했다. ClassicBox 가구를 네 번 연속 이동하는 동안 `Pending=1 Published=1 HoldingLighting=1 LightingGeometryCurrent=1`을 확인했고, 제외된 프로브는 최종 30개였다. 다른 두 방의 SH는 변하지 않았고, 마지막 전체 재계산 비교는 일치했다. [검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_pending.json)

이 기능은 갱신 대기 중 화면 연속성을 위한 근사다. 새 BVH는 프로브와 표면 사이의 차폐를 반영하지만, 이전 간접광 에너지나 색 번짐까지 즉시 고치지는 않는다. 제외된 프로브 주변은 일시적으로 어두워질 수 있다. 이후 지역 irradiance 갱신과 부분 게시로 이 대기 시간을 줄인다.

## 반복별 irradiance의 지역 갱신 — 2026-11-05

`r.PRTGI.Runtime.RegionalIrradiance=1`은 각 Jacobi 반복의 결과를 보관하고, 다음 지오메트리 갱신에서 영향받지 않은 결과를 같은 반복 번호에서 재사용한다. `RegionalTransport`도 자동으로 켠다. 첫 반복은 광선 표를 검증하며 모두 계산한다. 이후에는 교차·직접광 계산이 바뀐 출발 표면, 이전 반복에서 값이 바뀐 삼각형에 의존하는 표면, 완화 계수로 인해 자신의 이전 값이 달라진 표면만 irradiance를 재평가한다. 삼각형 안의 어느 표본이라도 바뀌면 그 삼각형을 참조하는 표면을 갱신하므로, 직접 이동 영역 밖의 간접광 변화도 전달된다.

최종 조명을 초기값으로 넣는 방식과 달리 반복별 이력을 사용해 고정 반복 횟수의 기준 결과를 유지한다. ClassicBox 이동에서는 13,560개 표면×반복 평가 중 5,616개를 재사용했다. 이동·회전·0MiB 예산 복귀의 최종 SH는 irradiance 전체 반복 계산과 CSV가 일치했다. GPU 해석 검사에는 광선이 그대로여도 반사광 공급 표면이 변하면 수신 표면을 다시 계산하는 사례를 포함했다. 빌드와 자동화 20개가 통과했다. [검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_irradiance.json)

기본값은 0이며 추가 이력과 마스크 예산은 `r.PRTGI.Runtime.IrradianceBudgetMB=16`MiB/방이다. 재사용에는 이전·새 이력과 작업 마스크가 함께 예산에 들어가야 한다. 반복 수·완화 계수·표면 슬롯이 맞지 않거나 완료된 이력이 없으면 전체 반복으로 복귀한다. 이력은 표면 슬롯 용량×반복 수×16바이트다. 모든 표면 그룹은 계속 디스패치하며 영향 검사 후 재평가를 건너뛰므로, 절약한 평가 수를 프레임 성능 향상률로 해석해서는 안 된다.

## 완료된 프로브의 부분 게시 — 2026-11-05

`r.PRTGI.Runtime.ProgressiveProbes=1`은 irradiance 반복을 모두 마친 뒤 프로브 투영 결과를 배치별로 읽어 게시한다. 아직 계산하지 않은 프로브는 이전 유효 SH를 유지하거나, 유지 가능한 배치가 없으면 무효로 표시한다. 반복 중간의 irradiance를 최종 조명으로 게시하지 않는다. 게시 직전 장면 세대를 다시 확인하므로, 가구를 다시 움직이면 이전 세대의 나머지 배치는 폐기된다. 기본값은 0이다.

8개 프로브 배치의 통합 검사에서 512개 중 먼저 게시된 부분은 최종 CSV와 같았고, 다른 두 방은 변하지 않았다. 부분 게시 뒤 재이동한 결과도 전체 광선 재계산과 CSV가 일치했다. 첫 게시 0.764초, 전체 완료 5.345초는 해당 검사에서 관측한 값이며 성능 비교치는 아니다. `PartialProbes`, `PartialUpdates`, `FirstPartialSeconds`로 진행도를 확인한다. UE6 빌드와 자동화 21개가 통과했다. [검증 보고서](../Plugins/PRTGI/Tools/validation_runtime_progressive.json)

## PC 기능·성능 검증 — 2026-11-05

2026-11-05 PC 회귀 검사는 이동·회전·추가·삭제와 방 분리를 포함한다. 이동·회전은 전체 재추적 대비 방별 상대 L2 및 최대 정규화 오차 `1e-6` 미만을 통과했고, 추가·삭제는 전체 재추적으로 복귀하여 CSV가 일치했다. 다른 두 방은 네 경우 모두 세대와 SH가 변하지 않았다. 이 비교 기준은 같은 반복형 Surfel solver의 전체 계산이며, 경로 추적 정답이나 기존 기준 구현과의 약 10.5% 차이를 해결했다는 뜻은 아니다. 메모리 예산을 낮췄을 때 재사용하지 않는 이전 irradiance 이력을 계속 보유하던 경로도 수정했다. 광선 표만 공유하는 별도 이력으로 교체하고, 호출자가 가진 원본 이력은 수정하지 않는다. GPU 해석 검사에서 0바이트, 새 이력만 들어가는 600바이트, 정상 예산 복귀를 확인했다. 전체 자동화 21개, 캐시 해석 세부 사례 24개가 통과했다. GPU 자원 해제는 렌더 스레드 순서를 따르며, 예산은 엔진 전체 할당이나 드라이버의 순간 메모리 상한을 의미하지 않는다.

세 방의 완료된 광선 표 합계는 약 40.32MiB, 반복별 irradiance 이력은 1.5625MiB다. ClassicBox 갱신 시 이전·새 irradiance 이력과 두 마스크 합계는 668,800바이트다. 장면 검사 중 Windows GPUProcessMemory 15회 표본에서 에디터 프로세스의 전용 GPU 메모리 최대 관측값은 약 3,418.72MiB였다. 이는 엔진·텍스처·렌더 타깃을 포함하는 프로세스 전체 값이며, 플러그인 단독 사용량이나 실제 순간 최대치가 아니다.

## 지원 범위와 남은 작업

현재 지원하는 것은 불투명 정적 메시 자산의 인스턴스 변환과 방향광·역제곱 감쇠 포인트 라이트다. 메시의 Mobility는 Movable이어도 된다. 포인트 라이트 밝기는 UE의 단위 변환을 사용하고 cm를 m로 환산한다. 광원의 색온도와 간접광 강도를 반영한다.

현재 제외되는 것은 스키닝, WPO, 시간·월드 위치·인스턴스별 입력에 의존하는 재질, MID와 런타임 재질 파라미터 변경, 정점 페인팅, masked/translucent, 스포트·렉트·하늘광, 발광 전송, 정반사 GI다. 재질 차트는 유한 해상도의 근사이며 원본 텍스처 해상도를 보장하지 않는다. 에셋의 불투명 표면과 UV 기반 재질을 사용해 검증한다.

이 단계에는 에셋 캐시의 디스크 직렬화·쿠킹, 자동 프로브 clipmap, 방 내부의 국소 프로브 무효화, Surfel LOD, GPU BVH 갱신, Radiance Cascade 방향 병합, 시간 누적·노이즈 제거, 모바일 fallback이 없다. Surfel 공간 해시는 위의 선택적 표면 풀에만 적용된다. CPU의 계산 대상 BVH 재구성과 차트 배열 병합, SH 읽기, 픽셀별 BVH 가시성은 정확도 비교를 쉽게 하기 위한 기준 경로이며 최종 성능 구조가 아니다.

후속 구현은 기준 SH와 화면을 보존한 상태에서 진행한다. 선택적 지역 irradiance 재사용과 프로브 부분 게시를 추가했지만, 전체 표면 디스패치·전체 프로브 투영과 공간 근사 오차는 남아 있다. 다음은 독립 실행 환경에서의 재측정, 화면 합성의 가시성 조회 및 제출·완료 확인·프로브 게시 비용 축소, 삼각형 경계의 보간과 표본 밀도 검증이다. 조회용 방향별 가시성 캐시와 시간 필터, 자동 clipmap·Radiance Cascade와 모바일 확장은 이후 단계다. 모바일에서는 메모리·정밀도·대역폭·저사양 fallback을 별도로 검증해야 한다.
